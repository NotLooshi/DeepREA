# Evidence-led investigation

Use this procedure when selecting what to inspect or when plausible interpretations compete. Keep it proportional to the question.

## Establish the evidence boundary

Bind findings to artifact hash/build, relevant configuration/resources, provider and analysis profile, and coordinate system or module identity. An address alone is not a stable cross-build identity. A shipped default is not necessarily the effective runtime value: trace overrides and precedence when they affect the answer.

Preserve raw tool results or retained Evidence references separately from interpretation. Page a retained result instead of repeating its producer. If a preview is truncated, record that boundary and recover the necessary view before treating it as complete.

Tag consequential claims as observed, inferred or unknown and cite their exact source. Static observations concern code or bytes; runtime observations concern the stated input, state and window. A missing string/import/handler or unobserved request supports only the searched boundary, not whole-program absence.

## Select a discriminating next read

Start from a feature entry point, meaningful literal, interface boundary or relevant format field. Use the smallest overview necessary to select a short list of promising locations. For each candidate, name the question it could settle and the evidence that would distinguish interpretations. High reference count is a prioritization hint, not proof of importance.

Trace trigger → handler → boundary → worker → effect only as far as the requested behavior requires. Record unsupported links explicitly; matching channel names alone need not prove dispatch. Inspect packaged resources/configuration when behavior depends on them. Stop when the requested claim is established within scope or the next step reaches an unavailable boundary; return the bounded result and missing evidence.

## Interpret without losing provenance

Keep structural names until semantic meaning is supported. Attach original identity, offset, access width and supporting sites to a proposed field/type/name. Equal offsets do not establish the same object type; different access widths can reflect partial access. Trace allocation, base pointers and callers to discriminate.

For suspicious decompilation, first check architecture, slice, mapping, function boundaries and coverage. Treat pseudocode as derived evidence, not original source. A fixed-size copy or missing local check is a candidate defect until caller, initialization, size and lifetime obligations are examined. State the smallest check that would refute the proposed interpretation.

## Bound obstructed work

For apparent flattening, opaque predicates, dead computation, encoded strings or split call chains, define the needed semantic question and a task-appropriate attempt/time bound. Preserve original and transformed views. Justify simplifications under actual integer widths, overflow, signedness, side effects and exceptional paths; do not discard unresolved transitions to obtain a clean-looking rewrite.

When the bound is reached without useful progress, record the unresolved frontier and move to a cheaper neighboring or runtime route when it can answer the question. Requeue only after a changed premise: new caller evidence, decoded data, corrected selection or improved tool capability. A new worker or higher self-rated confidence alone is not changed evidence. No fixed layer count proves a function impossible.

## Resolve a runtime uncertainty

Before authorized execution, state the question, exact target/action, input/state, supported duration or stop bound and what each plausible result changes. Use the bundled runtime guide for capture ownership, environment, observation scope and cleanup. Capture tooling is not a security sandbox. Retain raw outputs and identity, distinguish attribution from coincidence, and preserve unobserved branches. Stop at the declared supported bound and report incomplete cleanup or coverage.
