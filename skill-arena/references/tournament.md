# Select by the job, then optimize the library

The deliverable is a smaller, tested portfolio covering the user's work, plus explicit unresolved coverage. Instruction differences and a duplicate inventory alone do not establish value or finish this task.

## Map the whole scope

Inventory all authorized roots and create a persistent queue outside discovery. Each family records the job/outcome, installed candidates, external shortlist, required scenarios, tool compatibility, source identities, current phase, evidence, selected portfolio, retirement mapping and next action. Track queued, discovering, testing, selected, consolidated, blocked and unresolved states separately. A single-purpose skill without a competitor still needs a recorded coverage/disposition decision, not an invented tournament.

Group by user jobs, not identical names or prose. For example, UI skills described as Stitch, Impeccable, Emil Kowalski or design-taste may compete on producing a usable interface even when their instructions differ. Resolve each exact package identity rather than guessing from a brand or an ambiguous name such as “awesome design.” Inspect actual capabilities: a tool-specific design-system extractor and a page builder may be distinct stages. Test whether their added stage improves the end result before calling them indispensable or redundant.

Prioritize the user's most consequential/high-overlap family, not whichever permits the easiest check. Use the same scope through the queue; do not quietly substitute a glossary edit for UI production. Assign each skill a disposition and list any multiple-family dependencies before retirement.

## Expand first, select second

Include installed competitors and discover relevant external contenders before final selection. Temporary growth happens only in staging. Pin sources and preserve packages, dependencies, licensing and local modifications using discovery.md. External popularity is a search signal, not an advantage in scoring. Unavailable native tools make that workflow untested here; disclose any common-tool adaptation as a separate arm.

Use staged rounds when many candidates exist: common representative briefs for screening, repeated diverse briefs and a fresh holdout for finalists. Freeze screening/elimination rules and resource limits before outputs; do not permanently retire a skill on one cheap preliminary result. Untested installed candidates stay explicitly queued. Do not test every pair if common tasks give an adequate comparison. Test a skill combination only when it has a concrete plausible complementary benefit; account for its additional effort and dependencies.

## Benchmark what the skills actually do

The task must exercise the candidate's core promised outcome. Builders create working artifacts, reviewers find real defects and support repairs, debugging skills diagnose/fix actual faults, and document skills produce usable documents. Reading instructions, counting rules, answering self-evaluation questions or performing a trivial shared subtask is not a substitute.

For UI candidates, use materially different briefs such as a product landing page, a dense dashboard, and a constrained redesign. Execute the real workflows with matched inputs and budgets; inspect rendered desktop/mobile outputs and actual interactions. Separate mandatory gates (correct functionality, required content, accessible interactions and no unauthorized side effects) from comparative quality (visual hierarchy, typography, spacing, coherence, brief fit, responsive behavior, motion where useful, and measured effort).

Use anonymous rendered artifacts for comparative visual judging; reviewers receive the same brief/rubric, not candidate names, popularity or claimed scores. Retain rationale and disagreements, and describe model review as model judgment. Functional tests alone cannot crown a UI winner; visual preference alone cannot excuse broken required behavior. Use human judgment where a material subjective disagreement remains. Missing rendering/interaction tools means that part is unverified, not silently replaced with source-code aesthetics.

Freeze family-specific quality priorities, meaningful-improvement thresholds and practical-equivalence tolerances before trials. Run multiple representative briefs and repeat decision-driving cases. Include a no-explicit-skill baseline where feasible. If everyone passes everything on easy tests, label a ceiling effect and run a separately frozen, relevant harder round within budget, or leave the family unresolved. Do not declare equivalence from absence of a detected difference. Do not tune a contender on the holdout or rewrite scoring after viewing outputs.

## Retain the smallest adequate portfolio

First eliminate candidates that fail mandatory requirements for the proposed retained scope. Among eligible candidates, prefer repeatable outcome advantages under the frozen priorities. Preserve a specialist only when actual tasks establish necessary coverage or a material advantage missing from the champion. Record the specific winning cases and routing boundary; extra wording or an untested capability claim earns a test, not permanent retention.

For practical equivalence, require adequate representative/specialty coverage, repeated outcomes within the predefined tolerances, and no unresolved mandatory regression. Then prefer fewer active skills and a simpler setup, using measured effort/dependency burden and migration cost as declared tie-breakers. Do not equate shorter prompt length with better performance. If alternatives remain indistinguishable, a stable existing candidate can be retained while redundant alternatives are reversibly archived after dependency and activation checks. This is an equivalence-based consolidation, not a superiority claim.

Test the proposed final portfolio on a fresh end-to-end task and affected callers before retirement. A specialized candidate's role can be lost when a broad skill is removed even if their main tasks overlap; check the capability map. Preserve originals and use consolidation.md for supported mutation, verification and rollback. Every retired skill must have a concrete replacement or evidence-backed redundancy decision. Never uninstall unrelated plugin tools just to reduce a skill count.

## Finish the queue, not just the first comparison

After selecting and verifying a family, record the result and move to the next actionable family automatically within the authorized overall budget. A blocked family does not prevent unrelated ones from progressing. Use bounded batches as execution units, not as permission to silently narrow the whole objective. No implicit financial authority or background scheduler is created.

At a budget/capability boundary, save the exact queue, completed decisions, remaining families, blockers and next bounded action; report PARTIAL. “Fully optimized” is unsupported while relevant families remain untested or unresolved. When all scoped entries have supported dispositions and all requested consolidation checks pass, report the achieved coverage, before/after active counts, measured quality changes, demonstrated specialties and limitations. A smaller tested portfolio can be a success without every retained skill proving universal superiority.
