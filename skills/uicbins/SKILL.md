# UICBINS — UI Can't Believe It's Not Slop

One-shot means one user handoff with internal planning, implementation, repairs and review. Delegated reviewers are permitted; first drafts are not finished work.

## Scope and preparation

Infer BUILD, REFINE, REVIEW or PLAN. BUILD includes internal repairs; REVIEW reports without editing; PLAN ends at a buildable direction. REFINE revisits affected decisions. Preserve supplied facts, assets, wording, architecture, accepted direction and external-action permissions. Scale the record to the task. Do not add features merely to satisfy a checker.

Keep a project-local brief, blueprint, test inventory, source identities and evidence. Follow applicable test-first rules. Before implementation, establish the actual browser/test route and record the executable or tool that works. Pass that route to reviewers. Do not install dependencies automatically. Tool failures and missing rendering remain verification gaps.

For a new build or substantial visual change, read [design toolkit](references/design-toolkit.md). It supplies the page/app routes, pinned Taste direction library and executable inspection. Its house-style suggestions are contextual: user intent, accessibility and task completion take precedence. A measured failure, style disagreement and unsupported measurement are different results.

For blueprinting and QA, read [rendered outcome coverage](references/rendered-review.md). Build a supplied-fact ledger, run the automatic text-boundary scan, and actually open the resulting phone/intermediate/desktop images. Invalid-form feedback and prolonged automatic motion need adverse checks; geometry alone cannot approve visual quality.

## 1. Deepen the brief and blueprint

For adapting a website supplied by URL, read [reference adaptation](references/reference-adaptation.md) before deriving decisions. Screenshots alone do not activate it. Return findings to this blueprint; Pro is optional depth, not a capability dependency.

Briefly state what a strong practitioner would add within scope, which primary facts/assets ground the task, which methods/tools fit, and what observable evidence establishes success. Rewrite the execution brief without expanding the product.

For public pages or explicit SEO work, read [content and discovery](references/content-and-discovery.md) before composition. Separate supplied facts, assumptions and proposed choices. Inventory distinguishing subject details and available imagery. Write each section as a useful claim plus its evidence, or an app region as a user task plus its data. Choose a concrete direction through the toolkit; preserve existing brand constraints. Do not blend incompatible directions or invent proof to fill a composition. Define type, colour, spacing, imagery and purposeful motion together.

Define each consequential transition by its precondition, action and resulting data, visible content, focus, feedback and error state. Before handlers, turn task-required terminal fields and focus targets into executable expectations; assert them again after the final action and a second transaction, not only on the review screen. Test both surviving and removed targets when filtering or re-rendering changes the view. Blueprint meaningful components: purpose, content/source, hierarchy, asset, desktop/phone relationship, semantic role/name, states, transitions, keyboard/focus and acceptance outcome. Define reusable components once. Include relevant invalid, pending, error, edit, cancel, retry and post-success states. Write task-outcome expectations before implementing handlers; tests must not simply mirror the implementation.

For commercial pages, make the offer, commitment and next step intelligible. Recommend discoverable cost information. If undecided, ask once whether prices, a range, pricing link or explained quote/evaluation route belongs; continue independent work. Respect deliberate omission. Unanswered advice alone is not a blocker. Never invent amounts, benefits, testimonials or service conditions.

## 2. Build a complete slice

Build the visual idea and primary journey together, then inspect desktop/phone before expanding. Treat confirmation as a submitted snapshot: any contributing input change invalidates it, or inputs remain protected behind a working Edit path. Enumerate actual form controls, including names/emails; do not wire only the obvious selectors. Preserve a checkpoint before QA.

Use native buttons for actions and links for destinations. Keep labels, focus, contrast, status and semantic relationships truthful. Creative overlap must preserve legibility and operation. Motion must be interruptible, with stable resting styles and reduced-motion behaviour covering scripts as well as CSS. Preserve required artwork and animation while repairing defects.

## 3. Functional and access QA

Read [outcome checks](references/completion-checks.md). Run saved task tests for valid completion, invalid retry, edit/change/reconfirm, cancel/new transaction and relevant duplicate or asynchronous paths. For submitted native forms, run the toolkit's mutation checker against every contributing control. Custom widgets need separate assertions; unsupported coverage is not a pass. Use the state probe from outcome checks after consequential transitions and at phone width: verify surviving focus, retained task information and truthful status. These narrow checks do not replace journey tests.

Run the toolkit inspector on the actual delivered build. Repair objective findings; retain raw findings and disposition contextual advice through rendered review. Never hide checks with blanket exceptions. Measure relevant contrast pairs, inspect overflow/clipping and actual states across wide/narrow screens, short heights, supported themes/zoom, keyboard focus and reduced motion. Unsupported paint stays unresolved until appropriately inspected. Use WCAG 2.2 AA as the default design target, not a conformity claim.

## 4. Adversarial review and repair

Before dispatch, read acceptance reconciliation and the reviewer execution handoff in [final checks](references/final-checks.md). For new builds, use a fresh reviewer when delegated review is supported. Give the brief, final artifact, viewport captures, working browser route and task expectations, not the builder's verdict. Require actual adverse journeys and the composition disposition from [rendered review](references/rendered-review.md). If one browser launch fails, check the supplied route before declaring access unavailable. Without delegation, label a separate same-agent challenge.

Challenge specificity, composition, hierarchy, typography, imagery, content truth and interaction clarity. Record each objection as observation, consequence and falsifiable closure check. No objection quota or self-awarded winning score. Repair the highest-impact findings, preserve passing behaviour and rerun affected checks. After two unsuccessful fixes, investigate the cause rather than repeating blindly.

## 5. Final verification and delivery

Read [final checks](references/final-checks.md). After the last edit, run the finish command with the saved journey and mechanical checks, applicable discovery checks and all delivered files. Inspect final wide/narrow renders. Poll running test sessions instead of launching duplicates. Save actual output, exit status, viewport/state and current artifact hash. A screenshot, report schema, model review or mechanical pass alone does not establish completion.

Complete the published-claim audit from content and discovery for public copy. Before ending, apply the continue-or-handoff decision in final checks; pending required review or verification remains work to do. Reconcile brief, blueprint, controls and evidence. Continue through fixable defects; real access, authority or budget boundaries remain partial/blocked. Deliver the artifact, concise evidence index, first/final distinction and implemented versus simulated or untested limits. Do not claim universal quality, conversion uplift or superiority.

This package includes the complete workflow and tools. UICBINS-Pro adds selected specialist guidance without exclusive functionality. No helper grants publishing, installation or outreach authority or provides host-protected enforcement.
